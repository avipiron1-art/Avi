# Shiftly – מערכת לניהול עובדים, משמרות, נוכחות ומשימות

מערכת Web מלאה (Full-Stack) בעברית וב-RTL לניהול כוח אדם בעסק: עובדים, סידורי עבודה, שעון נוכחות, משימות, בקשות עובדים, התראות, דוחות ויומן פעולות.
המערכת עובדת מקצה לקצה – כל הנתונים נשמרים בבסיס נתונים, ההרשאות נאכפות בשרת, והממשק מותאם למחשב ולטלפון.

## הפעלה מהירה

דרישות: Node.js 20 ומעלה.

```bash
npm install
npm run build      # בניית ממשק המשתמש
npm start          # http://localhost:3000
```

בהפעלה הראשונה נוצר בסיס נתונים (`data/shiftly.db`) עם נתוני דמו.
לאיפוס הנתונים לנתוני הדמו: `npm run seed`.

פיתוח עם טעינה חמה: `npm run dev` (שרת על פורט 3000 + Vite על http://localhost:5173).
בדיקות אוטומטיות: `npm test`.

## העלאה קבועה וחינמית ב-Google Cloud (גם מהטלפון)

Google Cloud מציע שרת קטן (e2-micro) בחינם לתמיד, עם דיסק קבוע של 30GB – הנתונים נשמרים, והשרת לא נרדם.

1. **פתיחת חשבון** – נכנסים ל-https://console.cloud.google.com עם חשבון Google, מאשרים את התנאים ומגדירים חשבון חיוב (נדרש כרטיס אשראי לאימות; בגבולות השכבה החינמית אין חיוב). למנויי Google AI Pro יש גם קרדיט חודשי ל-Google Cloud שאפשר להפעיל דרך https://developers.google.com/profile.
2. **יצירת השרת** – בתפריט: Compute Engine ← VM instances ← Create instance:
   - Region: ‏`us-central1`, ‏`us-west1` או `us-east1` (רק אזורים אלה חינמיים)
   - Machine type: ‏**e2-micro**
   - Boot disk: ‏**Debian 12**, סוג **Standard persistent disk**, גודל **30GB**
   - Firewall: מסמנים **Allow HTTP traffic** ו-**Allow HTTPS traffic**
   - לוחצים **Create**.
3. **התקנה** – ליד השרת שנוצר לוחצים **SSH**. בחלון שנפתח מדביקים את הפקודה ולוחצים Enter:
   ```bash
   curl -fsSL https://raw.githubusercontent.com/avipiron1-art/Avi/main/deploy/gcp-setup.sh | sudo bash
   ```
   הסקריפט שואל אם להתחיל עם נתוני דמו, ואם לא – מבקש לבחור סיסמה למשתמש `admin`.
4. בסיום מוצגת כתובת בסגנון `https://34-123-45-67.sslip.io` – זו כתובת המערכת (עם HTTPS). שומרים אותה במסך הבית בטלפון.

**עדכון לגרסה חדשה:** מריצים שוב את אותה פקודה בחלון ה-SSH. הנתונים נשמרים.
**גיבוי:** גיבוי יומי אוטומטי נשמר בשרת בתיקייה `/var/backups/shiftly` (14 ימים אחרונים).
**שימו לב:** אם השרת נעצר ומופעל מחדש, כתובת ה-IP עשויה להשתנות – מריצים שוב את הפקודה כדי לקבל את הכתובת החדשה.

## העלאה לאינטרנט (Render) – גם מהטלפון

1. פותחים את https://render.com/deploy?repo=https://github.com/avipiron1-art/Avi ונרשמים עם חשבון GitHub.
2. מאשרים ל-Render גישה לריפו, נותנים שם לשירות ולוחצים **Deploy Blueprint**. ההגדרות נקראות אוטומטית מהקובץ `render.yaml`.
3. אחרי כמה דקות מתקבלת כתובת בסגנון `https://shiftly-xxxx.onrender.com` – נכנסים אליה עם משתמשי הדמו.

> **מגבלות התוכנית החינמית:** השרת נרדם אחרי 15 דקות ללא שימוש (הכניסה הבאה לוקחת כחצי דקה), ובסיס הנתונים **מתאפס לנתוני הדמו** בכל הפעלה מחדש או עדכון. לשימוש אמיתי עם שמירת נתונים: משדרגים את השירות לתוכנית בתשלום, מוסיפים Disk (למשל ב-`/var/data`) ומגדירים משתנה סביבה `DB_FILE=/var/data/shiftly.db`.

### משתמשי דמו

| תפקיד | שם משתמש | סיסמה |
|---|---|---|
| מנהל ראשי | `admin` | `Admin1234` |
| מנהל משמרת | `michal` / `ori` | `Manager1234` |
| עובד | `yossi`, `noa`, `shira`... (כל העובדים) | `Employee1234` |

בעמוד ההתחברות יש כפתורי כניסה מהירה לכל אחד מהתפקידים.

## התקנה כאפליקציה (טלפון ומחשב)

המערכת היא אפליקציית רשת מתקדמת (PWA), ואפשר להתקין אותה כמו כל אפליקציה, בלי חנות אפליקציות:

- **אנדרואיד / מחשב (Chrome, Edge):** בכניסה למערכת מופיע באנר "התקינו את Shiftly", וגם כפתור "התקנת האפליקציה" במסך הכניסה ובתפריט. לוחצים ומאשרים.
- **אייפון / אייפד:** פותחים את המערכת ב-Safari, לוחצים על כפתור השיתוף ובוחרים "הוספה למסך הבית". הכפתור במערכת מציג את ההוראות.

אחרי ההתקנה מופיע אייקון במסך הבית, והמערכת נפתחת במסך מלא. עדכונים לשרת מגיעים לאפליקציה אוטומטית. כשאין חיבור מוצג מסך "אין חיבור" ידידותי, והנתונים עצמם תמיד נטענים מהשרת.

## הרשאות

| הרשאה | מנהל ראשי | מנהל משמרת | עובד |
|---|:-:|:-:|:-:|
| צפייה בעובדים | ✓ | ✓ | – |
| הוספה/עריכה/מחיקה של עובדים, צפייה בשכר | ✓ | – | – |
| הערות מנהל | ✓ | ✓ | – |
| צפייה בכל המשמרות | ✓ | ✓ | המשמרות שלו |
| יצירה ועריכה של משמרות | ✓ | – | – |
| עדכון נוכחות, דיווח אירועים | ✓ | ✓ | החתמת שעון עצמית |
| ניהול משימות | ✓ | ✓ | עדכון סטטוס למשימות שלו |
| אישור בקשות | ✓ | – | הגשת בקשות |
| דוחות, הגדרות, משתמשים, יומן פעולות | ✓ | – | – |

המנהל הראשי יכול ליצור תפקידים חדשים עם הרשאות משלהם (למשל "קופאי" או "מנהל אזור"), לשנות שם והרשאות של כל תפקיד, ולמחוק תפקיד מותאם (המשתמשים שלו מועברים לתפקיד אחר) – בהגדרות ← הרשאות, ובנוסף אפשר להוסיף או להסיר הרשאות למשתמש מסוים בלבד (הגדרות ← משתמשים ← סמל המגן). בניית סידור עבודה (`schedule.manage`) שמורה כברירת מחדל למנהל הראשי, שיכול להעניק אותה למנהל משמרת ספציפי. כל בדיקה מתבצעת בשרת (`requirePerm` / סינון שאילתות לפי המשתמש); הממשק רק מסתיר את מה שאין הרשאה אליו.

## רשת סניפים: תחומי אחריות

לכל תפקיד מגדירים **מה מותר לו** (הרשאות) ו**על מי** (תחום אחריות), בהגדרות ← הרשאות:

| תחום אחריות | דוגמה | על מי ההרשאות חלות |
|---|---|---|
| כל הרשת | מנהל ראשי, מנהל תפעול | כל הסניפים וכל העובדים |
| הסניף שלו | מנהל סניף | כל העובדים בסניף שלו |
| סניפים שבוחרים | מנהל אזור | הסניפים שנבחרו למשתמש |
| המחלקה שלו בסניף שלו | מנהל מטבח – סניף חיפה | המחלקה שלו בסניף שלו בלבד |
| המחלקה שלו בכל הסניפים | שף ראשי של הרשת | המחלקה בכל הסניפים |
| רק במשמרות שבהן הוא אחמ"ש | אחמ"ש | רק בזמן המשמרת שהוא מוביל, ורק על העובדים שבה |
| רק על עצמו | עובד | הדברים של עצמו |

- הסניף והמחלקה של מנהל נלקחים מכרטיס העובד שלו, או נקבעים במשתמש (הגדרות ← משתמשים). מנהל אזור – בוחרים לו סניפים.
- עובד יכול לעבוד בכמה סניפים ("עובד/ת גם בסניפים" בכרטיס העובד) – הוא יופיע בלוח השיבוץ ובסידור של כל הסניפים שלו.
- המחלקות משותפות לכל הרשת (מטבח, בר, שירות…), והתפקידים/סוגי העובדים (מלצר, טבח…) לא קשורים למחלקה.
- **כל ההגבלות נאכפות בשרת**: עובדים, משמרות, סידור עבודה, נוכחות, בקשות, משימות, הודעות, דוחות, חיפוש וניהול משתמשים. גם ההתראות (איחור, בקשה חדשה, בחירת משמרת…) נשלחות רק למנהלים שאחראים על אותו עובד/סניף.
- **סידור עבודה לפי סניף**: לכל סניף לוח שיבוץ, דרישות מאיוש ופרסום משלו.
- **סוגי משמרות לפי סניף**: יש משמרות משותפות לכל הרשת, וכל מנהל סניף (עם הרשאת בניית סידור) יכול להוסיף משמרות לסניף שלו, לשנות משמרת משותפת רק לסניף שלו (נוצרת גרסה של הסניף) או להסתיר אותה בסניף – בלי להשפיע על סניפים אחרים. שינוי משמרת משותפת לכל הרשת – רק למי שאחראי על כל הרשת.

## אבטחה

- **סיסמאות** – bcrypt (cost 12), מדיניות סיסמה חזקה.
- **Sessions** – טוקן אקראי של 256 ביט ב-Cookie מסוג `HttpOnly` + `SameSite=Strict` (+ `Secure` ב-production); בשרת נשמר רק ה-hash של הטוקן. תפוגה, ניתוק כל המכשירים בשינוי/איפוס סיסמה, השבתת משתמש או שינוי תפקיד.
- **CSRF** – Double-submit token בכל בקשה שמשנה נתונים.
- **Rate limiting** להתחברות ולאיפוס סיסמה, ונעילת חשבון זמנית אחרי 5 ניסיונות כושלים. הודעת שגיאה זהה למשתמש שלא קיים (ללא חשיפת משתמשים).
- **SQL Injection** – כל השאילתות פרמטריות (prepared statements); עמודות מיון מתוך רשימה סגורה.
- **XSS** – React מבצע escaping, Content-Security-Policy קשיח (helmet), ולידציה לתמונות (`data:image` בלבד).
- **ולידציה בצד השרת** – zod לכל קלט, עם הודעות שגיאה בעברית לכל שדה, ו-CHECK/FOREIGN KEY בבסיס הנתונים.
- **Audit log** – נשמרים משתמש, פעולה, מועד, ערך קודם וחדש ו-IP. היומן בלתי ניתן לעריכה גם ברמת בסיס הנתונים (Triggers שחוסמים UPDATE/DELETE). רק המנהל הראשי יכול למחוק היסטוריה (הכול או רק פעולות ישנות), באישור סיסמה, והמחיקה עצמה נרשמת ביומן.
- **ייצוא** – הגנה מפני CSV/Formula injection.
- **אימות דו-שלבי** – TOTP (RFC 6238) עם חסימת שימוש חוזר בקוד, 5 ניסיונות לכל כניסה, קודי שחזור שנשמרים כ-hash. **Passkeys** (WebAuthn) עם אימות ביומטרי חובה.
- **סודות** – מפתחות Push, פרטי Google ו-tokens לא נחשפים ב-API.

## ארכיטקטורה

  db/seed.js          נתוני דמו
  middleware/auth.js  Sessions, הרשאות, CSRF
  lib/                זמנים, ולידציה, חישובי נוכחות, שדות משותפים
  services/           audit, notify + push, permissions, settings, reports, payroll (+ export),

  routes/             auth (+2FA, passkeys), dashboard, employees, shifts, attendance, tasks, requests,
                      notifications, reports, search, schedule, swaps, announcements, invites/join,
                      calendar, backup, admin (users/settings/meta/audit)
  tests/              בדיקות אינטגרציה (node:test)

  lib/                api client, auth context, toast, פורמטים ותוויות

- **Backend**: Node.js + Express, SQLite (better-sqlite3, WAL).
- **Frontend**: React 18 + React Router + Vite, Recharts, lucide-react, CSS מותאם עם Design Tokens (בהיר/כהה).
- **בסיס נתונים**: `roles`, `role_permissions`, `users`, `sessions`, `password_resets`, `employees`, `departments`, `positions`, `locations`, `employee_notes`, `shifts`, `attendance`, `incidents`, `tasks`, `requests`, `availability`, `notifications`, `audit_logs`, `settings`.
  זמני התכנון נשמרים רק במשמרת וזמני הביצוע רק בנוכחות; שעות, איחורים ושעות נוספות מחושבים ולא נשמרים כפולים.
- **משימות רקע** (`services/jobs.js`) – כל דקה: זיהוי עובדים שלא החתימו כניסה (התראה למנהלים ולעובד), תזכורת לסיום משמרת, משימות שמתקרבות ליעד וגיבוי לילי ל-Google Drive.

המבנה מודולרי ומוכן להרחבה:

- **אפליקציית עובדים** – כל הפונקציונליות חשופה כ-REST API תחת `/api`.
- **אינטגרציות** – `services/notify.js` (התראות + Push) ו-`services/mailer.js` הן נקודות ההרחבה לאימייל/SMS/WhatsApp.

## גיבוי ל-Google Drive (הגדרה חד-פעמית)

הגדרות ← גיבוי. במסך יש הוראות צעד-אחר-צעד. בקצרה:
1. ב-Google Cloud מפעילים את **Google Drive API**.
2. ב-**Google Auth Platform** יוצרים מסך הסכמה (External) ולוחצים **Publish app** – אחרת החיבור פג אחרי 7 ימים.
3. יוצרים **Client** מסוג **TVs and Limited Input devices**, ומדביקים את ה-Client ID וה-Client secret במערכת.
4. "חיבור ל-Google Drive" ← נכנסים ל-google.com/device, מקלידים את הקוד ומאשרים.

המערכת מקבלת גישה רק לקבצים שהיא עצמה יצרה (`drive.file`), ושומרת את הגיבויים בתיקייה **Shiftly Backups**. שחזור: מורידים קובץ `.db.gz`, פותחים (gunzip), ומחליפים את קובץ בסיס הנתונים כשהשרת כבוי.

## שליחת מיילים (Gmail)

הגדרות ← מיילים. מפעילים אימות דו-שלבי בחשבון Google, יוצרים **סיסמת אפליקציה** ב-myaccount.google.com/apppasswords, ומדביקים אותה יחד עם כתובת ה-Gmail. אפשר גם כל שרת SMTP אחר.
המערכת שולחת: קישורי איפוס סיסמה, הזמנות לעובדים ומייל "ברוכים הבאים", התראות חשובות (שיבוץ/שינוי/ביטול משמרת, בקשות, החלפות, הודעות דחופות – מקובצות למייל אחד לדקה), התראות אבטחה (שינוי סיסמה, כיבוי אימות דו-שלבי) והתראה למנהלים אם הגיבוי הלילי נכשל. כל משתמש יכול לכבות התראות במייל בפרופיל.

## התראה כשהשרת נופל (Google Cloud Monitoring)

שרת שנפל לא יכול לשלוח התראה בעצמו, ולכן Google בודקת אותו מבחוץ (חינם):
1. ב-Google Cloud: **Monitoring ← Uptime checks ← Create uptime check**.
2. Protocol: **HTTPS**, Hostname: הכתובת של המערכת (למשל `35-238-208-233.sslip.io`), Path: `/api/health`, Check frequency: 5 דקות.
3. ב-Response validation אפשר להוסיף "Content matches" עם `"ok":true` (הבדיקה מוודאת גם שבסיס הנתונים עונה).
4. ב-Alert & notification יוצרים ערוץ **Email** (וגם אפליקציית Google Cloud בטלפון אם רוצים Push), ושומרים.
מעכשיו, אם האתר לא עונה כמה דקות ברציפות – מגיע מייל/התראה.

### הערות לסביבת Production

- הגדירו `NODE_ENV=production` (Cookies מאובטחים) והפעילו מאחורי HTTPS.
- `DEMO_MODE=false` – קישור איפוס הסיסמה לא יוחזר ב-API; חברו שליחת מיילים בהגדרות ← מיילים.
- `APP_URL` – כתובת המערכת (קישורי איפוס והזמנה, Push, וטביעת אצבע – חייבת להיות בדיוק הכתובת שבה נכנסים, ב-HTTPS). `DB_FILE` – מיקום קובץ בסיס הנתונים. `PORT` – פורט.
- ייצוא PDF מתבצע דרך חלון ההדפסה של הדפדפן ("שמירה כ-PDF") עם עיצוב הדפסה ייעודי, כדי לשמור על עברית ו-RTL תקינים.
